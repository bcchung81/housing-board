# 데이터셋 스키마 (사업 원장)

화면(메뉴 7개·파생 상세·지도)이 읽을 자료를 표 단위로 정한 것이다. 스키마는 `schemas/ledger/*.schema.json`(JSON Schema 2020-12), 변환·검증은 `tools/ledger/`, 시험은 `tests/js/ledger.test.cjs`.

- **결정(2026-10-10, 사용자 승인)**: ① 팀 공통규격 v1.4(정책 → 프로그램 → 사업, CSV 8종)를 핵심으로 쓰고 화면이 요구하는데 v1.4 에 없는 것만 넓힌다. ② LH 준공예정 블록은 시군구를 찾은 블록에만 사업 id 를 주고, 못 찾은 블록은 검토 목록에 둔다. ③ 저장은 지금처럼 저장소 JSON + 스키마. 표 단위로 정규화해 DB 로 옮길 때 1:1 이 되게 하고, DB 전환은 기관 입력(쓰기) 화면을 만들 때 정한다. ④ 이번 범위는 스키마·이 문서·지금 자료의 변환 검증까지. 화면 코드와 수집은 그대로다.
- 근거: `/sources` 화면(화면별 사용, 종합상황판 위젯 8행, 지도 20행, 추가 확보 API 11·파일 6, 단계별 데이터 연계), 스펙 9장(사업 레코드·레지스트리·원천 카탈로그), `docs/analysis/주택공급상황판_데이터설계_정리본.html`(전국 수집 규모).

## 1. 화면에서 거꾸로: 무엇이 필요한가

종합상황판의 SAMPLE 위젯 6개와 지도의 미연결 2행이 요구하는 것은 다섯 가지로 모인다 — 전국 사업 원장, 일정 기록(당초·변경·현재와 월별 이력), 기관 입력(계획 호수·지연 사유), 시도·시군구 경계 단순화본, 정책·프로그램.

| 화면 | 질문 | 읽는 표 |
|---|---|---|
| 종합상황판 · 총리 지시 | 지시별 진척 | policies · programs · links |
| 종합상황판 · 월별 공급 파동 · 선택 시점 판정 | 6단계별 호수, 지연 | projects · events · units |
| 종합상황판 · 지연·주의 추이 | 지연이 늘었나 | events(observed_month 이력) |
| 종합상황판 · 전국 17개 시도 | 어디를 먼저 | projects → areas(시도) + 경계 단순화본(파일) |
| 종합상황판 · 월별 실적 흐름 | 계획대로인가(실적) | stat_facts |
| 종합상황판 · 향후 12개월 | 앞으로 공급 | events(COMPLETION·PLANNED) · units |
| 종합상황판 · 기관별 진행 | 기관별 진척 | projects.agency_id · units(AGENCY_PLAN) |
| 사업 · 사업 상세 | 사업의 단계·규모·위치·근거 | projects · project_locations · identifiers · events · units |
| 공급 실적 · 시도·기관 상세 | 시도·시행주체별 실적 | stat_facts · agencies (+ LH 블록의 events·units) |
| 보고자료 | 월간 브리핑 | stat_facts · events · units |
| 우리 동네 | 내 시도의 준공 예정·진행 사업·공고 | events · projects · notice_links |
| 지도 | 위치·단지·공고 | areas · project_locations · complexes · identifiers (+ 실시간 조회) |
| 데이터 원본 | 모든 숫자의 출처 | sources |

## 2. 관계

```
areas: 00 전국 ─▶ 시도2 ─▶ 시군구5 ─▶ 법정동10 ─▶ (PNU19: project_locations.pnu)
                         │                │
policies ─▶ programs ─(links)─▶ projects(PRJ-시군구5-일련4) ◀── project_locations
                                  ├─ identifiers: 건축HUB 관리번호 · LH 지구|블록 · 번들 단지
                                  ├─ events: 단계 × 예정/실제 × 당초/변경/현재 × 관측 월
                                  ├─ units: 준공예정·공고·공사규모·허가·기관 계획 호수
                                  ├─ complexes: 단지·블록(상태 5종·공정율)
                                  └─ agencies: LH·GH·SH·지자체·국방부 ── stat_actor ──┐
notices(공고 ID) ─(notice_links, 사람이 확인)─▶ projects                               │
stat_facts(지표·시도·월·시행주체) ── 원장과는 (시도, 월, 단계)로만 만난다 ◀──────────────┘
sources ── 모든 행의 source_ref
review_required ── 원장에 바로 넣지 못한 원천 레코드
```

| 표 | 기본 키 | 참조 | v1.4 |
|---|---|---|---|
| areas | area_code | parent_code → areas | 확장 |
| agencies | agency_id | — | 확장 |
| policies · programs | local_policy_id · local_program_id | — | 같은 열 |
| links | (link_type, from, to) | policies · programs · projects | 같은 열(link_type 값은 제안) |
| projects | local_project_id | sgg_code → areas, agency_id → agencies, superseded_by → projects | 글자 칸 대신 코드 칸 |
| identifiers | (id_type, id_value) — 같은 원천 레코드는 한 사업에만 | projects | + as_of, 확장 id_type |
| project_locations | (사업, 법정동, 필지) | projects, bjd_code → areas, pnu 앞 10자리 = bjd_code | 확장(v1.4 는 PNU·BJD 를 식별자에 둠) |
| complexes | complex_id = `{slug}/{단지 id}` | projects | 확장 |
| events | — (행 = 관측 한 번) | projects · complexes | + plan_basis · observed_month · complex_id · event_year · change_reason · change_note |
| units | — | projects · complexes | + complex_id, 확장 quantity_type |
| notices · notice_links | (notice_system, notice_id) | projects | 확장 |
| stat_facts | (metric, sido_code, ym, actor) | sido_code → areas, stage_code = 지표의 단계 | 확장 |
| sources | source_ref | — | + record_count · license · used_by · is_demo |
| review_required | — | projects(있으면) | 같은 열(review_type 값은 제안) |

- 코드는 모두 문자열이다(앞자리 0, 관리번호 6·7·13·22자리 — 스펙 9.1).
- 단계: 사업 단계는 `projects.stage_code`, 단지 상태 5종은 `complexes.status` 로 둘 다 둔다. 한 사업의 단지들이 다른 상태일 때 사업 단계를 정하는 규칙은 아직 미결이다(스펙 9.2).
- 물량은 기준이 다르면 더하지 않는다(PUBLIC_PLAN·NOTICE·PROJECT_PLAN·PERMIT·AGENCY_PLAN).

## 3. 보관할 것과 실시간으로 가져올 것

규칙 세 가지: ① 화면이 전국·시도 합계를 보이면 페이지마다 원천을 부를 수 없으니 **보관**(배치)한다. ② 과거 값이 필요하면 원천은 현재값만 주므로 **월 스냅샷으로 보관**한다 — 기록을 시작한 달부터만 지연을 셀 수 있다. ③ 한 위치를 볼 때만 필요하고 이력이 필요 없으면 **실시간 + 캐시**.

| 표·자료 | 방식 | 근거(확인한 수치) |
|---|---|---|
| events | 보관 · 월 스냅샷(빠뜨리면 안 됨) | 원천이 현재 예정일만 준다. 당초 대비 지연(Q3)·단계별 머문 기간(Q2)은 관측 이력으로만 계산된다 |
| projects · identifiers · units · project_locations | 보관 · 월 배치 | 건축HUB 는 법정동 단위 조회만 된다: 전국 18,865 단위, 주택인허가 기본개요 약 31만 건·약 2.1만 호출, 키 1개 하루 1만 → 2~3일 |
| stat_facts | 보관 · 월 1회 | 통계누리 4표 65,878행·약 2 MB. 모든 화면이 전국·시도 합계를 쓴다 |
| LH 준공예정(→ events·units) | 보관 · 연 1회 | 351행(278 지구·블록)·29 KiB |
| areas · 경계 단순화본 | 보관(연·반기) + 실시간 보정 | 법정동코드 53,387행 · SGIS 경계 |
| notices · notice_links | 목록은 실시간(1시간 캐시), 사업 연결·모집 일정만 보관 | 공고 캐시 535건 |
| complexes | 보관(지역 번들) | 22단지 |
| 건물 윤곽·필지 형상·건물대장·버스·정류소·지형·신설학교 | 실시간 + 캐시(원장 표 아님) | 위치마다 필요하고 이력이 필요 없다. 건물 윤곽 캐시만 80,550건 |
| policies · programs · links · AGENCY_PLAN | 보관(기관 입력 CSV) | 원천 API 가 없다 |

| 표 | CSV·파일(보관) | 외부 API | 기관 입력 |

## 5. 공통규격 v1.4 와 다른 점 (팀 합의 필요)

- `events.plan_basis`(BASELINE·REVISED·CURRENT)와 `events.observed_month`(찍은 달): v1.4 의 `date_type` 은 그대로(PLANNED·ACTUAL) 두고 열을 더했다. 이것 없이는 지연을 셀 수 없다.
- 2026-10-10 보강(수집 계획 5절): `events.event_year`(건축HUB 예정일이 연도만 오는 경우), `events.change_reason`·`change_note`(기관 입력의 일정 변경 사유: PERMIT·BUSINESS_APPROVAL·CONSTRUCTION_START·OTHER), `sources.is_demo`(가상 기관 입력을 실데이터와 가르는 표지 — v1.4 의 is_demo 는 내보낼 때 여기서 채운다).
- 지역 코드 칸(`projects.sgg_code`)·공공 판정 근거(`public_basis`)·필지 범위(`project_locations.pnu_scope`: SITE·REPRESENTATIVE)는 v1.4 변환 때 낸 보완 제안 3·4·5 를 반영한 것이다.
- 넓힌 값: id_type `HUB_HS_PK`·`HUB_AP_PK`·`MANUAL`, quantity_type `PERMIT`·`AGENCY_PLAN`, link_type·review_type 값(v1.4 에 허용값 없음).
- v1.4 는 PNU·법정동·사업번호도 식별자 표에 두지만, 원장에서는 각각 `project_locations`·기본 키다. 팀 제출용 CSV 로 낼 때는 다시 식별자 행으로 펼친다.

## 6. 지금 자료의 변환 결과

`node tools/ledger/convert.js [--month 2026-10] [--lh-sgg <매핑>] [--hub-events <스냅샷>] [--legal-dong <법정동코드 원본>] [--out <폴더>]` — 표별 행 수와 검증 결과를 보이고, `--out` 이면 검증을 통과했을 때만 표 파일을 쓴다. 2026-10 기준 표 한 벌은 `schemas/ledger-2026-10/tables/`(수집 계획 참고). 아래는 수집 전 자료만으로 변환한 2026-10-10 결과다:

| 표 | 행 | 비고 |
|---|---|---|
| projects | 77 | 레지스트리 그대로(건축HUB 55 = PROJECT·공공 여부 UNKNOWN, 번들 22 = BLOCK) |
| identifiers | 80 | 건축HUB 관리번호 58 + 번들 단지 22 |
| project_locations | 82 | 필지 있는 행 + 법정동만 아는 행 |

| units | 75 | 허가 세대수 55 + 단지 20(모집공고 7·준공예정 1·허가 12) |
